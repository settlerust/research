# LLMs at the Catan table

DeepSeek won five of our first ten comparison games, Kimi three, and GLM two.
Inkling won none. No model won a majority. The interesting differences were
not just in strategy: agents varied in how reliably they used tools, remembered
the board, negotiated for resources, and acted before their time expired.

The open-source arena lets language models play complete games of Catan through
tools. The Rust engine enforces the rules; the models choose what to do. Every
round below opens the full 3D game. Its **Spectate** tab separates private notes
and returned reasoning from public conversation and game actions.

## What a player sees

Each seat receives a system prompt identifying its player, opponents, time
budget, and available tools. Its observation includes its own resource and
development cards, public scores and card counts, bank supply, offers, and
recent events. Opponent hands, notebooks, future cards, and random seeds remain
outside the player's view.

The board arrives in several consistent representations: tile resources and
numbers, coordinate rows, vertex adjacency, road endpoints, ports, and legal
actions. Models configured for vision also receive a rendered 2D board image.
The replay uses the game's normal 3D viewer; the image supplied to a player is
a separate input representation.

## A turn is an agent loop

The TypeScript harness gives an active player two minutes by default. It can
make several calls within that budget. Inference, search, and tool execution
all spend the same clock, and each tool response includes the remaining time
and a fresh observation.

| Tool | What the player can do |
| --- | --- |
| `play_action` | Build, buy or play cards, move the robber, roll, and propose, accept, reject or counter a trade through a typed action union |
| `analyze` | Rank legal moves with expectimax and learned n-tuple values, or study another seat using sampled hidden information; choose a time budget and depth |
| `chat` | Talk to the table or selected opponents; conversation alone does not execute a trade |
| `notes` | List, read, write, append or delete private documents by slug |

The engine rolls automatically before the loop when the player has no playable
knight. With a knight available, the model decides whether to play it before
rolling, including the robber destination and victim. Returning no tools ends
the activation; in the main phase, the harness records an end-turn action.
Unfinished mandatory decisions use the engine's recorded timeout rule.

Off-turn players can negotiate, chat, take notes, and analyze. In this series,
they received 15-second spectating windows every four turns and when new offers
arrived. An offer can expire or be taken by another player while a model is
thinking, so a rejected tool call does not always mean an illegal strategy.

## Memory lasts across turns

Each seat keeps its own conversation history across active and spectating
windows. After 20 decision cycles, or when the history exceeds 60,000 characters,
the harness compacts older exchanges and retains up to four recent ones. A bounded
model summary falls back to an extractive summary when necessary. Memory starts
fresh for each game.

The suggested documents are `plan`, `strategy`, `friends`, and `enemies`. Their
latest contents are loaded into that seat's system prompt on each request.
The notebooks can hold long-term plans and grudges, but they are the agent's
account of the game, not an authoritative ledger. We observed notes that
miscounted earlier trades or returned to an already-blocked settlement site.

## The first ten-game comparison

All four models ran through Baseten. Each game used a distinct board seed and
the same frozen harness, tools, learned search checkpoint, and two-minute active
budget. The schedule counterbalanced actual starting positions in four-game
blocks, giving each model two or three starts in each position over ten games.
Two games ran concurrently. All ten reached an engine-recorded winner; none
were replaced or excluded.

This is an exploratory comparison of these four configured agents. It is not a
comparison against the standalone search policy or a general model leaderboard.
DeepSeek received text representations; the other three also received images.
The exact model IDs and settings are available in the competition's details.
Earlier harness-development games are not included in this denominator.

DeepSeek's 50% win rate has a 95% Wilson interval of 24–76%. Kimi's interval is
11–60%, GLM's 6–51%, and Inkling's 0–28%. Ten games leave substantial uncertainty,
especially between the top three. Average finishing place follows the engine
winner, then final revealed points, averaging tied places. It describes the
finish, not the distance from an eventual win.

## What happened at the table

In [Game 6](/replay/baseten-series-2026-09-17-06), all ten completed trades
involved Inkling, which nevertheless finished last. Kimi privately called it a
“reliable trade partner” and marked GLM as hostile after robber attacks. On turn
39, DeepSeek refused Kimi's request for two ore. Inkling accepted a reduced
one-for-one offer, and Kimi immediately built a city. Cooperation was practical
and often asymmetric; these exchanges did not establish an alliance.

Kimi's [Game 9 win](/replay/baseten-series-2026-09-17-09) showed a sharper
tactical sequence: a turn-49 Monopoly collected nine wool, followed by a
settlement. On turn 57, taking Longest Road brought Kimi to 11 points. Its card
timing was not uniformly good: a lumber Monopoly in Game 5 collected nothing.

GLM combined three cities with both awards to win
[Game 8](/replay/baseten-series-2026-09-17-08). DeepSeek used several different
scoring paths across its wins: settlements and awards in Game 1, four cities
and Largest Army in Game 3, and a final development-card purchase in
[Game 10](/replay/baseten-series-2026-09-17-10). Some winning sequences depended
on favorable draws as well as planning.

## Reliability is part of the result

| Agent | Tool errors / calls | Engine timeouts | Private note updates |
| --- | ---: | ---: | ---: |
| DeepSeek V4 Pro | 22 / 906 | 36 | 129 |
| Kimi K3 | 41 / 1,060 | 9 | 101 |
| GLM 5.3 | 44 / 1,073 | 2 | 118 |
| Inkling | 319 / 936 | 11 | 0 |

Many DeepSeek and Kimi errors concerned offers that had expired or been taken.
Inkling's failures were more often malformed arguments, missing action fields,
and invalid board locations. Its 0/10 result combines strategy with substantial
tool-use difficulty. Engine timeouts include forced decisions such as discards;
they are not a count of whole turns lost. Provider latency and failed compaction
requests also affected execution.

All agents received automatic search advice, but they rarely requested more
analysis. The ten games contain only one completed explicit expert-search
report. A useful follow-up would separate tool reliability, time management,
and deliberate use of opponent analysis before attributing differences to
strategic reasoning alone.

## One file preserves the match

The arena writes an append-only journal during play and finalizes a single
Parquet file for each game. It retains the prompts, provider responses, returned
reasoning, tool calls and results, public events, private notebook revisions,
snapshots, failures, and engine outcome. The viewer seeks through that record
with the playback track and reconstructs each notebook at the selected time.

These research replays intentionally include all agents' private material for
inspection. A seated model never receives another seat's private record. Only
reasoning actually returned by the provider is shown; missing internal reasoning
is not reconstructed. API credentials are excluded from the archive.

<AgentContext title="Run a competition and publish its results">

The arena is a self-contained TypeScript repository with vendored Rust/WASM
rules, search, and learned tables. It requires Node.js 24 or later. Set
`BASETEN_API_KEY` and `BASETEN_BASE_URL` in `arena/.env`, then install and verify:

```sh
cd arena
npm ci
npm run verify
npm run models
```

Configure four players in `config/baseten.json`, then plan a fresh series.
Planning freezes the schedule and runtime without making inference calls.
Running it makes billable requests to the configured provider.

```sh
npm run tournament -- plan --id my-competition --matches 10 --concurrency 2 \
  --publish ../web/public/replays
npm run tournament -- run --directory runs/my-competition
npm run tournament -- report --directory runs/my-competition
```

The first comparison used series `baseten-series-2026-09-17`, completed on
September 17 in the operator's local time. The competition asset retains each
game's seed, board-seat assignment, opening order, regular turn order, final
points, winner, elapsed time, and Parquet SHA-256. Outcomes and file hashes were
checked against all ten original journals and static replay copies.

The schedule was frozen before play. This report and its qualitative transcript
interpretation were written afterward; they are not a preregistered hypothesis
test. Attribution: Codex implementation and audit, with transcript review by
`gpt-5.6-luna`.
